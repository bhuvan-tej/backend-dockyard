# LEARNING — Java 9-11 Features, Explained

This is the narrative companion to the endpoints — read this to understand
**why** each feature was added and how it actually works, not just what it
returns.

## 1. Why this app picks up where Java 8 left off

Java 8 (2014) was a massive release — lambdas, streams, `Optional`,
`java.time`. Java 9, 10, and 11 followed on a faster 6-month cadence with
smaller, more surgical additions, and **Java 11 (September 2018) is the next
LTS release after 8** — meaning it's the version most real migrations
actually jump to. This app covers the practical, REST-demoable subset of
what accumulated across those releases: `var`, small but frequently-tested
`String`/`Optional`/`Collection` additions, one-line file I/O, and a
standardized HTTP client.

## 2. var — local-variable type inference

`var` (JEP 286, **Java 10**) lets the compiler infer a local variable's
static type from its initializer, instead of you writing it out:

```java
var count = 42;                      // inferred: int
var label = "answer";                // inferred: String
var numbers = List.of(1, 2, 3);       // inferred: List<Integer>
```

### The most common misconception

`var` is **not** dynamic typing, **not** `Object`, and **not** "no type." The
compiler determines ONE concrete static type at compile time from the
right-hand side and bakes it directly into the bytecode —
`var list = new ArrayList<String>()` is exactly as strongly typed as
`ArrayList<String> list = new ArrayList<String>()`; the generated bytecode
is identical. `var` only removes redundant left-hand-side typing.

### Where var CAN be used
- Local variables **with an initializer**.
- Enhanced for-loop variables (the element type is inferred from the
  collection's generic type).
- try-with-resources resource variables.
- (**Java 11**, JEP 323) Lambda parameters — see below.

### Where var CANNOT be used
- Fields (instance or static).
- Regular method parameters (only lambda parameters, and only in Java 11+).
- Method return types.
- Generic type arguments (`List<var>` is illegal).
- A local variable with no initializer, or initialized to bare `null` with
  no cast (there's nothing to infer FROM).
- A lambda or unqualified method reference with no explicit target type —
  `var x = () -> 42;` fails because a lambda has no type of its own; it only
  gets one from a target functional interface.

### var in lambda parameters (Java 11, JEP 323)

This was added for one specific reason: **to let lambda parameters carry
annotations.** A bare, type-less lambda parameter (`x -> ...`) has no
annotation target at all — you'd previously have had to spell out the full
parameter type just to attach an annotation to it. `var` lets you keep type
*inference* while still allowing an annotation:

```java
BiFunction<Integer, Integer, Integer> sum = (@NonNegative var x, @NonNegative var y) -> x + y;
```

Every parameter in the list must use `var` consistently — you cannot mix
`var` and an explicit type in the same lambda parameter list.

## 3. New String methods

| Method | What it does |
|---|---|
| `isBlank()` | True if empty OR made entirely of whitespace — stricter than `isEmpty()` (length == 0 only) |
| `strip()` / `stripLeading()` / `stripTrailing()` | Unicode-aware whitespace removal, per `Character.isWhitespace(char)` |
| `repeat(int)` | Concatenates the string with itself N times |
| `lines()` | Splits on `\n`, `\r\n`, or `\r`, returning a `Stream<String>` |

### strip() vs the legacy trim() — the actual difference

`trim()` only strips characters `<= U+0020`. `strip()`/`stripLeading()`/
`stripTrailing()` use `Character.isWhitespace(char)`, which recognizes real
Unicode whitespace ABOVE U+0020 too — e.g. U+2003 (EM SPACE). `trim()`
leaves U+2003 behind; `strip()` correctly removes it.

**A gotcha worth knowing**: a few Unicode "space-like" characters —
U+00A0 (NBSP), U+2007 (FIGURE SPACE), U+202F (NNBSP) — are *deliberately
excluded* from `Character.isWhitespace()` (they're non-breaking by design),
so `strip()` leaves THEM behind too. "Unicode-aware" doesn't mean "removes
every character that looks like a space."

## 4. Small but frequently-asked functional/collection additions

- **`Predicate.not(Predicate)`** — a static factory that negates a
  predicate. It matters most for negating a **method reference** directly:
  `list.stream().filter(Predicate.not(String::isBlank))` — a bare method
  reference has no `.negate()` to call until it's already assigned to a
  `Predicate` variable. `predicate.negate()` (the pre-existing instance
  method) still works fine once you already have a `Predicate` in hand.
- **`Optional.isEmpty()`** — the logical inverse of `isPresent()`, added
  purely for readability: `if (opt.isEmpty())` reads better than
  `if (!opt.isPresent())`.
- **`Collection.toArray(IntFunction<T[]> generator)`** — lets you write
  `list.toArray(String[]::new)` instead of the older
  `list.toArray(new String[0])`. Both work; the generator form reads more
  clearly about intent (the JIT already optimizes the zero-length-array
  idiom well, so this is about readability, not performance).

## 5. java.nio.file additions

- **`Path.of(String, String...)`** / **`Path.of(URI)`** — a direct
  replacement for the older `Paths.get(...)` factory. `Path.of` exists so
  `Path` construction doesn't need to go through a *different* class
  (`Paths`) than the type it produces — `Paths.get(...)` still works and
  just delegates to `Path.of` internally now.
- **`Files.writeString(path, content, options...)`** /
  **`Files.readString(path, [charset])`** — read or write an entire file as
  a single `String` in ONE call, replacing manual
  `BufferedReader`/`BufferedWriter` boilerplate or a third-party helper like
  Apache Commons IO's `FileUtils`.

## 6. java.net.http.HttpClient

Standardized in **Java 11** (it existed as an incubator module in Java 9 and
10), replacing the old, famously low-level `HttpURLConnection` — no more
manually managing connection objects, output streams, or response-code
plumbing.

- **`client.send(request, bodyHandler)`** — **blocking/synchronous**. The
  calling thread waits until the full response has arrived.
- **`client.sendAsync(request, bodyHandler)`** — **non-blocking/asynchronous**.
  Returns a `CompletableFuture<HttpResponse<T>>` immediately; the calling
  thread is never blocked. You compose further stages
  (`thenApply`/`thenAccept`/...) exactly like any other
  `CompletableFuture` (see `spring-boot/14-multithreading` for a deep dive
  on `CompletableFuture` composition itself).

This app's HTTP demos target a **tiny embedded local server** (started
in-process via `com.sun.net.httpserver.HttpServer`) rather than a public
URL — the `HttpClient` usage is 100% real, only the target happens to be
local, so the demo never depends on external network access being
available.
